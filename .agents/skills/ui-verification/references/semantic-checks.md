# Semantic and visual checks

Use before visual acceptance. Start from the owner's actual wording and original native
frame. State the requested mismatch before selecting a fix or changing data. A full-ring
seam and a cyan pool drawn on another provider's band are different defects; solving one
does not close the other. Resolve ambiguity from the available evidence before guessing.

## Map meaning before judging appearance

Build a compact expected/observed mapping for every selected metric or pair, accounting
for missing items and unexpected rendered extras. Use the actual snapshot/summary and
owning surface contract. Include:

- provider family and logical metric ID, selected window/pool and its paired mate;
- family/half color, expected band/position and which side of a shared band it owns;
- reported value, remaining/used interpretation, status and optional purchased credits.

Verify the complete mapping against the native frame. Sorting or selection can move a
band while a retained half stays behind. Check each half's family AND radius, not merely
the number of arcs or whether a percentage changed. A Cursor secondary half sharing
Codex's band while its mate occupies another band is wrong even if counts/shapes look plausible.
Use the existing locked design/ordering rules; do not invent a new visual convention.

When a pair is removed, reordered or absent, verify that the previously occupied split
surface no longer draws stale data. Trace both configured split routes, not only the
currently visible first pair. Static arithmetic or a correct TITLE branch is producer/
resource evidence, not proof of the value delivered to the live bound renderer.

## Inspect actual original frames

View the original device/emulator frame, not only a scaled documentation export, preview
board, test status or screenshot filename. Identify the actual visible app/page/renderer
and compare it with the evidence's artifact identities. Review art can be correct while
the installed active face is older or uses retained bindings.

Judge the whole affected surface after the final change: every metric/half, legends,
units, clipping, default cells, status controls and navigation context relevant to the
case. Do not infer that uninspected neighboring elements are correct because one detail
passed. Verify real circle/screen boundaries before measuring or cropping.

For upper face cells, inspect EVERY rim's full contour and its clearance to neighboring
cells, time and bands in the original native frame, with a magnified view when needed.
Compare each border's gradient direction and the central border's uniformity with the
current owning design. Populated default cells do not prove clean rendering: look for
unexpected pale flecks, stray strokes and broken contours around them. Keep border fades,
unexpected artifacts and usage-progress arcs as separate checks. If a missed artifact is
reported after acceptance, preserve the incident frame, reopen the review and keep the
public capture candidate Pending until actual repair and matched native verification.

Use the actual unclipped native viewport and intended gesture region for interaction
measurements. Accessibility semantics may expose a clipped child rather than the full
page; a gesture sized from those bounds can fail without proving a navigation defect.
Distinguish actual system font/DPI state from an injected test density or animation scale.

## Match the case after changes

Preserve the failing input/state and compare like-for-like before/after frames after the
candidate is installed and active. Record an intentional state change as a separate case;
do not silently substitute different percentages, pair membership or a fresh fixture.
An observed success covers that target/state, not every device or retained-install path.

After temporary preferences or a fixture are restored, verify actual derived surfaces
again using the [state/artifact reference](state-and-artifacts.md). Restored file bytes
alone do not establish restored complications, widget caches or the active scene.

Healthy public examples follow user-docs. Preserve the incident privately when preparing
a clean demonstration; do not replace the incident with healthy data and call the bug
fixed. Public coherence is required independently of the incident's diagnostic value.
