# Update after every actual coordinator UI-verification mistake

Use whenever an owner re-report or actual evidence demonstrates that our UI conclusion
or verification procedure was wrong. Update this skill for EVERY such occurrence, before
issuing another acceptance claim. A repeated mistake is not exempt because a rule exists.

## Preserve and correct the failed decision

Keep a small sanitized case artifact in `LOCAL_ARTIFACTS/`: expected/observed behavior,
the incorrect conclusion, evidence that disproved it, affected state/artifact identities
and the reference/procedure correction. Preserve original native frames when safe. Do not
retain secrets, authentication frames, private profiles or sensitive provider payloads.

Correct the narrowest reusable decision or procedure that failed. Update this skill's
closest reference. If the operational fix belongs elsewhere, keep it there and correct
this skill's routing/verification trigger too. For an already-covered mistake, strengthen
the failed trigger or verification
step so that the new occurrence changes future behavior; a private log entry alone is not
an update to the skill. Do not accumulate duplicate checklists or a growing incident log
inside SKILL.md. Case details stay in the ignored artifact.

Examples of owning boundaries:

- Wrong defect/metric/band conclusion → semantic checks and its expected/observed mapping.
- New app but old active face, unproved split delivery, stale restoration cache → state
  and artifact checks with matched runtime evidence.
- Locked/charging UI mistaken for app data → route to android-devices/android-emulators;
  keep unlock/event recipes there rather than copying them into this skill.
- Empty default face cells, inconsistent neighboring captures, ordinary-showcase errors
  or Stale → user-docs; correct verification routing without duplicating public policy.

If a test/procedure was faulty, fix it under the existing authorship contract. Actual code,
test and helper changes require Runner execution and independent review; workflow prose
is delegated. A mistaken UI claim never authorizes implementation fallback or a new tool,
test framework, dependency, device reset or approval flow.

## Verify the correction

Recheck the preserved incident and matched before/after cases against the revised method.
For a substantive guidance change, arrange an independent forward-test with a realistic
request and minimum raw artifacts. Do not give the evaluator the intended answer or prior
diagnosis unless its task requires that context. Use read-only/isolated evaluation when
possible; this is not authorization for unrequested live device mutations.

After the last correction, repeat whole author review and all applicable skill validators,
citation/docs checks. The coordinator then independently reviews the complete result to
ZERO under delegation/finalization. Preserve unperformed device or causal checks as
Pending. Report what the revised procedure actually proved, not an assumed fixed product.
