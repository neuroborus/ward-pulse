# Planning research and concrete authoring

Use when preparing or reviewing an actual Runner plan that depends on technical contracts.
Keep the existing authorship, frozen-input, Native/HOST and independent-review boundaries.

## Select the repair during authoring

A substantive plan must choose a specific minimal technical candidate before execution:
identify what changes in the owning structure/behavior, why the available evidence and
contracts support it, preserved boundaries and corresponding meaningful regression coverage.
Repeating requirements while deferring the central technical choice to execution is not an
approved implementation plan. The actual Runner planner selects the candidate; the coordinator
supplies requirements/evidence, never a prewritten implementation patch or helper.

A proven incident cause is not required to choose an evidence-bound candidate. Separate the
observed failure, proposed mechanism and expected effect; preserve uncertainty and require
actual later acceptance. If an essential fact is missing, name it and explain its effect on
the choice instead of publishing requirements as though the repair had been selected.

## Supply usable primary-contract evidence

Before a fresh run, the coordinator uses an already authorized research route to supply the
necessary concise primary facts, links, version applicability and unavailable evidence in
the role-facing packet. Do not demand new unsupported Native read-only MCP/service/network
research. A bounded offline task can use its supplied primary brief and repository Source;
report genuinely missing evidence through the supported clarification/blocker route.
Do not copy manuals, expose private material or turn supplied facts into a presumed cause.
External research does not transfer code authorship or move mandatory HOST checks into Native.

## Interpret a rejected operation narrowly

One observed Native authoring revision failed with ERR_CODEX_ISOLATION and operation_mcp_tool.
That establishes a rejected operation at that isolation boundary, not which exact MCP tool
was called, a token/output-limit cause, or a capability limit for every tool/executor.
An isolated failure is not automatically a Runner defect; classify only what actual evidence
supports. Keep missing measurements and uncertainty explicit; do not inspect provider-private
storage to recover them or invent a hidden continuation.

Use only actual supported terminal actions. If no resume is offered, a fresh reviewed input
may supply missing primary context after the prior run releases ownership; do not blindly
retry its invalid plan. Never bypass isolation, change protected configuration/journals/state,
rewrite frozen inputs, or implement outside Runner. A new packet still needs a concrete
planning choice and independent review; copying the failed draft does not repair it.
